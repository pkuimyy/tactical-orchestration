## 1. MVP 的定位与最终演示

**MVP = 可通过 HTTP 驱动、由原生 Web 客户端操作的「军事学说实验场」最小闭环。** 它要证明：玩家可以构造一个小型六角战场、调整连队编制和团级默认学说、为一个旅建立有因果依赖的联合行动，运行多日 WEGO 模拟，借助可检索的日志理解行为，并对同一场景进行可复现对照实验。

### 最终必须能演示的完整流程

1. 在浏览器中打开或创建「河谷突破」场景；编辑地形、河流及桥梁、双方团与连队、HP、补给点、通信节点和合法的初始情报。
2. 为己方一个旅配置工兵、装甲、炮兵和步兵团；为装甲团选择「突破失败后后撤到已知可达补给点」的默认学说；设定旅级协作「架桥／火力准备 → 装甲突破」。
3. 同一冻结场景分别运行「旅部保序」与「团独立行动」方案；双方命令锁定后由 Server 结算，独立方案的顺序可能有利也可能不利，固定种子可重现。
4. 在地图、协作图和事件日志间定位同一动作，检查等待、桥梁状态、炮击、连级战损、撤退以及因果原因；切换师部／上帝视角，确认**只改变玩家观察，不改变部队决策**。
5. 查看单次和一组配对种子的描述性对照结果。只使用 cURL／Bruno 等 HTTP 客户端，也能完成相同的场景创建、运行与结果读取。

**完成定义：以上演示可在一台普通 PC 上离线运行，使用全新安装／构建环境可以按 README 重现；不依赖 Godot、JavaFX、专门 CLI、任何 JavaScript 框架或外部商业服务。**

## 2. 范围边界

### 2.1 必须实现（P0）

| 领域 | 最小范围 | 本次要验证的设计假设 |
|---|---|---|
| 六角地图 | 小型可编辑地图；平原、森林／高地、河流格边、桥梁、道路、城市／师部位、基础工事 | 地形和通行实际影响机动与战斗 |
| 军事编制 | 双方；城市固定师部、单个己方旅及旅部、若干团；团内多个混编连；步兵／装甲／反坦克／炮兵／工兵／侦察／通信基础能力 | 团是占格与行动单位，连决定其能力 |
| 战损与机动 | 连级 HP；同一组织度衰减函数；针对性防护／反击；最慢连决定正常作战形态下团速度；速度差约束追击 | 步兵填线与机械化装甲／侦察具有不同定位 |
| 日回合与交战 | 双方提交、锁定、一次结算；有限轮事件推进；同格争夺、遭遇、退却／驱逐的简化可测规则 | 同轮冲突不受集合遍历顺序操纵 |
| 默认学说 | 有版本的数据定义；突破失败→已知可达补给点整补；条件等待及明确备用动作；玩家可覆写关键参数 | 约定大于配置，失联单位仍能自主行动 |
| 旅级协作 | 单个战区／旅内 DAG；架桥→渡河、炮击→突击；前置依赖、失败分支、确认条件；无旅部的环境相关可复现调度 | 旅部以两个通信连占位换取指定任务保序，而非免费攻防光环 |
| 最小通信与情报 | 初始五格节点连接可配置；通信工事只有 HP；本地知识、师部共享知识分离；N 本地反应、N+1 正常共享、失联滞留 | 全知观察不能使单位作弊；正常共享无额外 N+2 等待 |
| 最小后勤 | 可编辑补给点及库存；撤退目的地选择；补给可用性影响休整或持续战斗的至少一项明确规则 | 补给点是地图设施而非凭空全图供应 |
| 实验与日志 | 冻结场景；单次运行、固定种子重放、两组学说／协同的配对种子对照；真相日志、观察和报告、决策依据 | 玩家能解释和比较计划与实际执行 |
| 客户端与接口 | Spring Boot HTTP／JSON；原生 HTML／CSS／JavaScript Web 客户端，自 M1 开始实现地图、场景编辑，后续迭代 DAG、日志和回放；本地认证 | Web 不参加结算，HTTP 可独立驱动 |

### 2.2 实现为实验近似值，但不得违反确定的设计原则

- **战斗公式**：用版本化、可替换的第一版确定性公式，而非声称已完成平衡；验证防守略占优势、伤害落到实际连队、有效反坦克反击、无反击的远程打击不凭空掉血。
- **组织度曲线／兵种数值**：允许第一版测试参数；共享同一 HP 比例衰减规则，不重复惩罚 HP 损失。
- **日内推进**：先用可配置上限（默认测试 4 轮）进行事件迭代；不把“四微阶段”变成玩家可见的固定行动顺序；记录到达上限未完成的任务。
- **运输**：MVP 支持「可编辑补给点和可达路径／补给规则」，**完整汽车／铁路运力调度、真实堵车和承运形态可延后**。数据模型保留独立运输状态，不通过混编战斗连偷偷加速。
- **战区**：至少可标记一个旅负责的战区并校验旅内 DAG 的归属。复杂边界跨旅作战不进入首个 MVP。

### 2.3 明确不进入本轮 MVP（P1／后续）

完整 60 天战役和实控区域价值计分、马拉松、完整 PvE 战略 AI、经济系统与科研树、旅容量逐步扩张至约 10 团、多旅跨战区联合行动、完整铁路／公路车队交通模拟、精细天气与世界生成、全套装备批次及调优、六维雷达的完整正式视觉效果、完善兵种能力专题图层、地图美术和音效、JavaFX／Godot 正式客户端、云存档／联机大厅／账号／反作弊、游戏发行安装包及最终 Source-Available 法律文本。以上**不能反向污染或阻断本轮模块边界**。

## 3. 实施约束及工程约定

1. **单一规则来源**：纯 Java 引擎维护权威 `WorldState`；Spring Boot 提供应用入口并承载 Web 静态资源；浏览器仅提交命令与展示投影。无独立 CLI 项目；cURL／Bruno 是正式调试入口。
2. **API 与 Web 纵向并行**：M1 开始每个里程碑同时落地最小 HTTP API 和可操作 Web 切片；场景编辑经专用 API 修改场景草稿，正式战局中界面不可私自写 HP、位置或推算真实敌情。
3. **先日志后动画**：所有有意义的状态改变产生结构化事件；任务调度与默认学说写明触发理由。MVP 可不做移动动画。
4. **场景与运行分离**：`ScenarioDraft → ScenarioRevision（冻结）→ GameInstance／ExperimentRun`；再次实验从冻结输入开始。
5. **稳定复现**：运行清单包含场景哈希、规则版本、双方命令、种子和随机算法版本；事件 ID／排序稳定；无并行线程竞态参与规则。
6. **安全边界**：本地仅监听回环地址、启动会话 Bearer Token、输入和资源限额，调试权限与正式游戏写命令分开。
7. **最小纵向切片**：M0 形成可调用服务；从 M1 起每个节点都须产出可在浏览器操作的功能、对应 HTTP 用例、自动测试和必要的日志实例；不接受只提交框架空目录。
8. **原生 Web 限定**：MVP 不采用 React／Vue／Angular／Svelte、jQuery、DAG／画布／状态管理等第三方 JS 框架或组件库；使用原生 HTML、CSS、ES Modules、Fetch、SVG／Canvas，构建与打包可先不设 Node.js 依赖。禁止在浏览器另写一套规则引擎。
9. **Web 部署**：MVP 优先由 Spring Boot 同源提供静态资源和 `/api/**`，减少跨域与双进程前端开发负担；本地启用会话 Bearer Token，Web 通过用户明确输入或受控启动方式取得，不提供无认证的取令牌 API。

## 4. 开发节点与验收门禁

> 节点严格按 **M0 → M1 → M2 → M3 → M4 → M5 → M6** 推进；满足前一节点验收后再扩大范围。工期由实际投入评估，不在此假设开发人数与速度。每个节点交付：可执行版本、自动化测试、至少一份可阅读日志／HTTP 请求示例、已知问题及下一节点输入。

### M0 — 工程骨架与 HTTP 安全入口

**开发内容**

- 初始化 Maven 多模块（使用全局 Maven，不提供 Wrapper）（`core`、`simulation`、`application`、`server`），统一 JDK／依赖版本、格式检查与 JUnit 测试。
- Spring Boot 可独立启动；暴露健康检查、从路由／DTO／校验注解生成的 OpenAPI（生成文件不纳入版本管理）／可执行 HTTP 回归请求及统一错误响应；定义场景、命令、事件 DTO 的版本策略。
- 本地监听 `127.0.0.1`；强随机启动令牌；受保护接口拒绝无效令牌；请求大小、基础参数校验；避免凭据进入日志。

**验收门禁**

- 从干净工作区运行构建与全部测试通过；`server` 可单独启动。
- cURL／Bruno 携有效令牌访问受保护 API 成功；不带／带错令牌得到 401；外网网卡默认不能连接。
- `core`／`simulation` 不含 Spring、JavaFX、Servlet 依赖；提供自动生成 OpenAPI、README 的 cURL 示例和 `scripts/smoke-test.py` HTTP 回归。

### M1 — 最小 Web 地图编辑与场景冻结

**开发内容**

- 六角轴向坐标及格边；地图、河流／桥梁、地形、道路、补给点、城市师部、双方团连和初始 HP 的 JSON 模型与校验。
- 场景创建、修改、读取、冻结 HTTP API；冻结版本不可变并具有内容哈希；从同一版本生成多个游戏实例。
- **从本节点同步开始原生 Web 客户端**：Spring Boot 同源托管 `index.html`、CSS 和 ES Modules；SVG 或 Canvas 绘制简易六角格；能够选择格子、编辑基础地形／河流格边／桥梁／补给点，放置和查看双方团连，并通过 Fetch 调用场景草稿 API。
- 首版页面可采用地图＋属性表单＋请求结果／错误提示三部分；不用框架、不做成熟美术、不要求此时已有战斗动画或完整 DAG 编辑器。
- 最小占格及建制校验：正常单团占格、师部不可移动、旅部拥有两个正式通信连、普通团可混编及不满编。

**验收门禁**

- 通过 **HTTP 请求和浏览器页面两条入口**，均能完成「创建地图→放置师部、工兵、装甲和补给点→冻结→启动两场独立实验」。
- 无效坐标、重复占格、非法编制、超限地图及修改已冻结版本返回有意义的 4xx 错误。
- 修改原始草稿不改变已创建游戏；冻结输入哈希稳定；场景可导出／导入并保持等价。
- Web 可清晰显示服务端返回的坐标、设施和编制；刷新页面后从服务端重新载入内容一致；非法编辑显示有意义的错误，不靠前端绕过服务端校验。

### M1.1 — 单屏游戏工作台（M1 后的界面修订）

- 以游戏工作台组织界面：地图为核心，侧边部署面板与底部实验/日志同屏，连接和新建场景使用弹窗。
- 至少适配 1980×1080 显示器，并验证常见浏览器可用高度；主界面尽量无滚动条，满编连队、实验与日志使用标签和分页。
- 保留 M1 的原生 Web、服务端校验、冻结和导入导出边界，不提前实现 M2 战斗/移动。
- 删除重复维护的 `.http` 手填样例，HTTP 验收由代码生成 OpenAPI 和可执行回归脚本承担。

### M1.2 — 战场管理

- 独立 header 页签提供战场搜索、分页、重命名、复制、归档／恢复和未冻结草稿删除。
- 复制只继承部署输入；管理写操作使用乐观版本检查。已有冻结版本的来源仅可归档。
- 保持单屏游戏工作台布局；浏览器和服务端测试覆盖管理与冻结来源保护。

### M2 — 一日 WEGO 结算及最慢连机动

**开发内容**

- 双方提交命令、确认、锁定、单日推进及合法生命周期；保证每局同一天至多结算一次。
- 连队装备形态与各地形通行／速度；团按最慢有效连统一移动；侦察高机动与装甲追击约束。
- 可配置的有限事件迭代、独立任务可复现调度、冲突集合；至少处理同格争夺、接敌与位置更新。
- 最低限度的 `WorldEvent`／`OrderTransition` JSONL 和规则版本／随机种子运行清单。
- 在 M1 Web 基础上增加「提交命令／推进一天」按钮与最简结算事件列表；不必在此节点完成时间轴回放。

**验收门禁**

- 4 装甲＋2 徒步步兵不能按装甲速度移动；步兵装备换为机械化后瓶颈被解除；不可通行连使全团不能穿越该路段。
- 同初始输入／双方命令／种子连续重跑，日志与最终状态哈希一致；更换调度种子能产生允许的时序差异。
- 速度 6 的已脱离侦察团，在同等路线、无包围条件下不因装甲团速度 5 恰好先调度而被追上。
- 在 M1 页面提交双方命令和执行结算，Web 事件列表与相同输入 HTTP 结果一致；重复点击不会重复结算。
- A、B 同轮争同一空格时，不因集合插入次序不同而改变谁免费获得守方地位；重复 `commit／resolve` 不重复推进。

**M2 实施状态（2026-09-27）**：已完成并通过规则／应用／HTTP／浏览器门禁。
采用默认 4 次、每次 15 内部时间单位的有限推进窗口；同刻意图统一判冲突后同步更新位置。
接敌只记录冲突并保持位置，战损与驱逐留待 M3；未完成路线次日重新下令。
运行清单与 JSONL、固定追击场景及黄金摘要已落地，详见 `docs/m2-wego.md` 与 `docs/MVP-acceptance.md`。

### M3 — 连级战斗、组织度与默认学说

**开发内容**

- 连级 HP、共用组织度曲线、按目标类型和防护计算损伤；守军展开／地形／简单工事、反击和退却／驱逐。
- 第一套受约束的团级学说：常规前进、遭遇反应、突破失败后撤向已知可达补给点、找不到补给点时备用动作；用户可覆写撤退条件／目标。
- `DoctrineDecision` 日志显示知识输入、命中规则、选择动作和原因；最小休整／补给可用性逻辑。
- Web 增加连队 HP／装备、团级学说选择与覆写面板；展示交战前后团位置、连级战损及学说决策原因。

**验收门禁**

- 可运行「2 装甲＋4 徒步步兵填线」对抗进攻团；战损落到实际连，步兵 HP、装甲防护和反装甲反击各有可辨识贡献。
- 同编制正面强攻已展开防守团，在选定基线场景中比攻击无准备同等部队承担更不利的代价；不将该实验结论泛化成全地图固定加成。
- 不会重复按 HP 损失和组织度对同一能力无意识双扣；无有效反击的远距炮击不导致开火方莫名掉血。
- 装甲突破失败自动退向**其已知且可达**补给点；更换未观察的隐蔽补给设施不改变它的选择。
- Web 展示团连战损和默认学说的命中规则；UI 不擅自计算与后端不同的组织度。

**M3 实施状态（2026-09-27）**：连级伤害、共用组织度、实际防护／反击、展开／工事、驱逐与歼灭已落地。
版本化默认学说支持阈值和补给目标覆写，参数跨日保存；规划器仅接收公开地形、本团状态与局部知识。
撤退消耗剩余时间；次日休整按库存恢复有效连 HP。Web 提供命令／学说／六连战况及可读决策依据。
规则／HTTP／浏览器门禁与固定摘要见 `docs/MVP-acceptance.md`，当前参数见 `docs/m3-combat.md`。

### M4 — 旅内 DAG、通信和情报完整验证

**开发内容**

- 单旅／单战区 DAG 校验及执行：两通信连、架桥→渡河、炮击→进攻；完成、失败、等待和备用分支。
- 世界事实、实际观察、已确认任务结果、报告送达分别建模；基础通信连／通信工事节点网络（初始测试半径 5）；损坏与断联。
- `RegimentKnowledge`／`BrigadeKnowledge`／`DivisionKnowledge`；团的本地条件反应；次日合法上传及指挥网络共享；师部／全知投影。
- 环境相关且可复现的**无旅部独立行动**时序；同种子配对对比协同方案。
- Web 增加旅级操作表单及**可读 DAG 视图**（原生 SVG／DOM 连线即可）；通信与已知情报切换和师部／全知视图切换，不要求复杂拖拽。

**验收门禁**

- 保序图中工兵尚未完成或后续团未合法确认时，装甲不会因后台世界状态更新提前通行；炮兵未完成准备时，装甲按已选失败分支处理。
- 无旅部情况下，存在事先约定／环境较好时自然保序以及不利条件下失序的可复现场景，不能硬编码为“必定失序”。
- 旅部被摧毁／失联后，已收到的团级任务可继续；未收到的任务不凭空执行；固定通信工事被摧毁会实际改变网络连接。
- 第 N 天局部接敌可以当日触发该团反应；正常第 N+1 天报告进入师部并可供合法连接单位使用；失联发现不泄露；没有多等到 N+2。
- 切换全知视图与师部视图，战斗决策及真实日志哈希不变。师部视角的失联团只有最后可信报告和时间。
- Web 可查看 DAG 各节点的已确认依赖状态、等待与失败分支，并可通过任务 ID 对应日志；即使不开完整地图回放也能验收。

**M4 实施状态（2026-09-27）**：单旅／战区 DAG、双通信连门禁、架桥与火力前置、已收任务和未收任务、失败分支已实现。
通信连与可毁固定工事共同构图；知识按团／旅／师分层，N+1 同边界送达与共享，失联滞留与复联补送。
服务端提供只读师部／全知投影，师部保留孤立部队最后报告日期与位置。原生 Web 增加协作表单、SVG DAG、工事编辑及通信显示。
52 项 JUnit、HTTP 同输入重放与固定摘要、三种视口的 Chromium 回归覆盖上述门禁。
日内计划继承 M2 的次日显式重下语义；不把未完成任务自动当成次日已送达任务。详见 `docs/m4-coordination.md`。

### M5 — 原生 Web Doctrine Lab 单次实验闭环

**开发内容**

- 整合自 M1 迭代的原生 Web 六角地图（SVG／Canvas）、地形／格边设施、团连、HP、补给、通信和初始情报编辑；地图可切换师部／全知观察。
- 团标最多两个具象兵种图标（主体、显著机动瓶颈）；团详情；旅级 DAG 先用可编辑任务表单及可阅读关系图，不要求自由拖拽工作流编辑器。
- Web HTTP 客户端适配：连接同源 Spring Boot、认证、加载／冻结场景、编辑学说、提交双方命令并运行；禁止 UI 持有权威模拟状态。
- 地图、任务节点、事件日志相互定位；按天／团／任务筛选并单次回放。若程序未提供战中全量状态快照，允许按日志与冻结输入重算回放。

**验收门禁**

- 在 Spring Boot 已启动并完成必要的令牌提供后，不需要 cURL／Bruno 即可通过浏览器完成第 1 节的单次河谷突破演示；服务不可用时给出明确错误与重试入口。
- 界面与同输入 HTTP 实验得到相同事件、同一最终状态；切换视图不会改变单位实际决策。
- 页面源码只用原生 HTML／CSS／JavaScript 与浏览器标准 API；无第三方 JS 框架、图形库和客户端规则引擎；通过基本浏览器手动验收及 HTTP 回归。
- 浏览器页面在服务端计算和读取大量日志时保持可操作、有执行中反馈；六角格在常用缩放下能看清团身份与两个以内的构成图标。
- 用编辑器保存后重开场景，地图／团连／学说／依赖关系不丢失。

**M5 实施状态（2026-09-27）**：原生 Web 已完成单次河谷实验闭环，新增初始情报编辑、首日方案另存／重开、主体与瓶颈 SVG 团标、按日历史回放及团／任务筛选联动。
回放来自服务端完整同时间批次快照；师部历史帧不提前使用 N+1 报告，观察不修改当前命令或权威结果。
56 项 JUnit、HTTP 双实例重放、完整 Chromium 流程与三种视口验收通过；详情见 `docs/m5-doctrine-lab.md`。
保存的是可导出的初始方案；战中持久化、批量 A/B 和多种子矩阵按 M6 继续。

### M6 — A/B 实验、回归套件与 MVP 发布门禁

**开发内容**

- 实验运行器支持冻结同场景、改学说／旅级协同配置、**相同种子配对**和多种子批量；日志、结果和规则版本归档。
- 结果展示最低包含：目标完成状态、完成天数、双方连级 HP 损失、等待／无效行动次数、依赖失序／失败次数、撤退去向；只做可解释描述性对比，不自动给某种学说万能评分。
- 固化测试场景和 HTTP 回归请求；保存与重载；单机 API 安全与异常输入测试；编写从零构建运行说明。

**验收门禁——MVP 通过条件**

- 下列七组场景全部具备固定输入、预期断言及可读日志：①架桥渡河；②炮火准备／突击；③突破失败／撤退补给；④侦察 6 vs 装甲 5；⑤2 装甲＋4 徒步步兵填线；⑥失联和 N+1 报告；⑦单连残编阻击／被驱逐。
- 相同输入连跑至少两次事件与状态完全一致；批量实验相同一组种子再次运行，逐次结果一致；能追踪任一结果对应的场景、学说、命令、种子与规则版本。
- 对相同场景的「有旅部／无旅部」配对实验，能从日志观察**顺序保障、等待成本与战损差别**；不要求有旅部方案每次都赢。
- 恶意或错误 API 输入被校验拒绝：无效 Token、超大地图／DAG、循环依赖、跨旅越权、未到结算条件、重复结算、危险导入路径。
- 一台新环境依照 README 能启动 Spring Boot 并用浏览器打开同源 Web 实验场，在离线条件下完成预置实验；所用构建依赖的获取／归档方式有清楚说明。

## 6. 验收度量及失败处理

**正确性优先于视觉。** 不用“看起来差不多”“一次打赢了”替代验收；对随机顺序采用固定种子断言＋多种子统计，避免把随机比例误认成单次保证。

- **P0 失败直接阻断后续节点**：日志无法重放、同输入不同结果、DAG 提前触发、隐藏情报被团级决策读取、重复 HTTP 结算、最慢连速度不生效。
- **P1 可记录后推**：图标细节、平滑动画、自由拖线操作、复杂地图生成、完整雷达视觉、批量实验的大型报表。
- **规则与内容分开维护**：测试参数或装备表调整允许改变战损数值，但改变既定原则（最慢连、N+1、旅部保序、防守倾向等）必须先更新 GDD 并说明迁移及回归影响。
- **性能先设可运行基准再定规模**：至少验证一张含数十团和数十天的预置实验不会令 Web 页面长时间无响应；首版不承诺大型开放战役的性能。
