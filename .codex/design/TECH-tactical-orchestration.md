**TACTICAL ORCHESTRATION**  
**胜兵先胜，而后求战**  
*Victory Is Prepared Before Battle.*

> 技术架构基线｜2026-09-27  
> 对应文档：[游戏需求设计](GDD-tactical-orchestration-requirements.md)。本文区分已确定技术方向与建议的 MVP 实现细节；接口示例为设计草案，尚非已发布协议。

## 1. 技术目标与非目标

### 1.1 目标

- 权威战场**只在服务端**维护与结算；客户端不直接修改真实战场状态。
- 服务端可以脱离图形界面启动；创建场景、提交双方命令、推进一天、读取日志和运行实验均可通过 HTTP 完成。
- 同一引擎支持单人游戏、军事学说实验、AI 客户端和未来联机，不为不同入口复制游戏规则。
- 相同初始场景、规则版本、命令、环境和种子得出相同事件轨迹与最终状态。
- 以真实事件、局部观察、情报送达及学说决策为独立记录，实现可解释性、回放与回归测试。
- 作为购买者可获得源码的 PC 游戏，支持离线启动、保存与构建相应发行版本。

### 1.2 MVP 非目标

不采用 Godot、JavaFX 客户端、第三方 JavaScript 框架或组件库、专用 CLI、分布式微服务、Redis／消息队列、复杂账户系统、专业兵棋符号作为默认 UI、复杂 3D／Shader 或强 DRM。未来联机相关的身份与权限边界保留，但首版不实现完整互联网大厅。

## 2. 确定的技术栈

| 领域 | 技术方案 |
|---|---|
| 主要语言 | Java |
| 权威模拟 | 不依赖任何 UI／Spring 的纯 Java 引擎 |
| 服务端 | Spring Boot 独立进程，HTTP + JSON |
| MVP 客户端 | 原生 HTML／CSS／JavaScript，通过 Fetch 调用同源 Server |
| 地图 UI | 原生 SVG／Canvas，逻辑六角坐标独立于像素坐标 |
| DAG 编辑／可视化 | 原生 DOM／SVG 表单、节点和连线；先可编辑可阅读，复杂拖拽延后 |
| HTTP 调试与 AI | cURL、Bruno 或任意 HTTP 客户端，不另开发 CLI |
| 构建 | 全局 Maven 3.9.x 多模块，不提供 Maven Wrapper；版本兼容要求见 README |
| 序列化 | 建议 Jackson + 版本化 JSON Schema／DTO |
| 日志／回放 | 结构化 JSONL，必要时配合状态快照 |
| 单元／集成测试 | 建议 JUnit、Spring Boot 集成测试 |
| 打包 | Spring Boot 可执行 JAR；M1 起同源提供 Web 静态资源，正式安装包延后 |
| API 文档 | springdoc 从路由、DTO、校验及必要注解生成；生成的 OpenAPI JSON／YAML 不纳入版本管理 |

当前工程采用 JDK 25、Spring Boot 4.0.8，依赖及插件版本在 Maven POM 中统一管理；全局 Maven 已验证 3.9.9。兼容版本和验证环境以 README 与验收记录为准。

## 3. 运行架构

```text
Native Web Client ┐
                  ├── HTTP / JSON ── Spring Boot Server
cURL / Bruno ─────┤                         │
AI Client ────────┘                         ▼
                                      Application
                                      ├── Command Validation
                                      ├── Scenario / Experiment
                                      ├── Turn Lifecycle
                                      └── View Projection
                                             │
                                             ▼
                                       Simulation Engine
                                      ├── World State
                                      ├── Regiment State Machines
                                      ├── Doctrine Evaluator
                                      ├── Brigade DAG Scheduler
                                      ├── Communication / Knowledge
                                      ├── Movement / Combat / Logistics
                                      └── Event Journal
```

- 原生 Web 仅发送命令、展示观察结果、编辑场景／学说、渲染地图和回放；没有可直接写入模拟引擎的捷径。
- Spring Boot 承担 HTTP、认证、参数校验、游戏实例管理、事务性命令用例与持久化适配，并同源托管 Web 静态资源。
- 核心引擎不引用 Spring Boot、JavaFX、Servlet 或 HTTP 对象；单元测试与大规模实验可在 JVM 内直接调用引擎，外部正式入口仍为 HTTP。
- MVP 本地部署为一个 Spring Boot 服务进程，浏览器打开其同源页面；客户端从 M1 起逐节点迭代，将来迁移远程服务不改写核心规则。

## 4. 推荐模块边界

```text
tactical-orchestration/
├── pom.xml                    # 全局 Maven，多模块聚合与统一版本
├── tactical-core/             # Hex、地形、连团编制、命令与不变量
├── tactical-simulation/       # 事件推进、战斗、机动、学说、DAG、情报
├── tactical-application/      # 用例、游戏实例、视图、实验管理
├── tactical-server/           # Spring Boot、HTTP、安全、存档适配
├── tactical-server/src/main/resources/static/ # 原生 Web 地图、DAG、日志与实验场
├── scenarios/                 # 版本化测试场景和预设
├── doctrines/                 # 默认军事学说和旅级任务模板
├── tests/                     # 跨模块场景／API 回归（可按工程实际组织）
└── docs/                      # API、构建、授权及规则说明
```

依赖方向为 `core ← simulation ← application ← server`；Web 只通过 HTTP 使用 API DTO，不访问服务端内部 `WorldState`，不复制规则引擎。依赖箭头仅表示“依赖于”，最终工程可以把稳定 DTO 抽出独立契约模块。

## 5. 领域数据模型

### 5.1 场景、游戏和冻结输入

- **ScenarioDraft**：实验场可任意编辑的初始地图、地形、阵营、团连、设施、知识、天气、学说和双方预置任务。
- **ScenarioRevision**：保存的场景版本；开始实验前冻结成不可变输入，计算内容哈希。
- **GameInstance**：某次运行；关联场景版本、规则版本、随机种子、双方命令、当前天数和状态。
- **ExperimentRun**：一组冻结场景与学说的单次运行；**ExperimentBatch**：一组共享控制条件、成对比较不同学说的运行。

正在运行的 `GameInstance` 绝不能因为用户后来编辑 ScenarioDraft 而改变初始条件。

### 5.2 地图与编制

```java
record HexCoord(int q, int r) {}
record HexEdge(HexCoord a, HexCoord b) {}
```

六角格采用轴向逻辑坐标；地图和格边的数据模型可表达河流、桥梁、道路、铁路、工事及其状态，不使用浏览器像素位置做游戏判定。

基础实体包括 DivisionHQ、Brigade、Regiment、Company、Facility、TransportAsset 和 SupplyInventory。师部与旅部的特殊身份通过能力与指挥关系建模，实际 HP 来自下属连队。一个团的占位关系作为权威世界不变量执行，不以 UI 堆叠决定。

连队保存 `type`、`equipmentBatch`、`maxHp`、`currentHp`、`experience`、装备／作战参数等；组织度由损伤函数推导。团速度在**给定通行条件**下取其有效连队速度最小值，不另发明固定的兵种职业速度。运输资产与团的 `transportState` 分离于正常作战编制。

### 5.3 知识模型

至少严格区分：

```text
WorldState        客观真实状态
RegimentKnowledge 团本地已知内容
BrigadeKnowledge  旅部已合法接收内容
DivisionKnowledge 师部已合法接收内容
```

单位状态机输入是本团实际可用于作战的己方状态、已接收命令、`RegimentKnowledge` 和当前合法可观察环境；**不得接收完整 WorldState 供学说任意查询**。师部视图、上帝视图和实验场调试视图由同一底层数据投影生成，切换玩家视图不会改变团级认知与 AI 行为。

## 6. 命令与默认学说

### 6.1 命令边界

区分三种写入：

1. **场景编辑命令**：修改尚未冻结的 ScenarioDraft，可编辑双方真实初始状态。
2. **战役命令**：在运行中的 GameInstance 提交合法的团任务、旅级协同、回合确认；不可直接设置当前 HP 和位置。
3. **实验／调试命令**：运行冻结输入、批量对照、查询全知状态或导出日志，不默认为正常联机权限。

对领域动作建模，避免 `PATCH /games/{id}/world` 等可以绕过规则的通用状态修改接口。

### 6.2 数据驱动的默认学说

学说应以版本化、受约束的数据表达：触发条件、可用观察字段、行动、完成条件、失败分支与默认选择。例：突破失败 → 选择**本团已知且可达**的补给点 → 撤退并休整；不存在有效点时执行预设备用方案。

不允许从实验场 JSON 直接加载并执行任意 Java／脚本。学说执行器输出结构化 `DoctrineDecision`，包括规则 ID、输入知识版本、触发条件、所选行动和解释。使用明确的规则优先级与冲突解决原则，以免不同默认行为在同一时刻相互覆盖。

## 7. 旅级 DAG 与行动调度

### 7.1 有限权限 DAG

每个 DAG 节点至少包含：`nodeId`、`operationId`、执行团、任务类型、目标、依赖列表、完成条件、失败条件、备用行为及状态。图必须无环，且节点团符合旅的战区与指挥权限；跨战区只允许有限定义好的支援接口。

需要明确区分：

- 客观执行结果（任务是否真实完成）；
- 协调器已确认结果（消息是否送达旅部）；
- 执行单位可据以行动的确认（团是否已合法观察／收到消息）。

引擎不能仅因为桥梁在 `WorldState` 已建好，就让尚不知情的远方装甲团自动触发依赖。

### 7.2 日回合引擎

建议集中式确定性离散事件调度，而非为每个团启动真实线程／进程：

```text
双方提交并确认当天命令
      ↓
锁定命令与已接收的旅级依赖
      ↓
重复推进符合条件的行动和遭遇事件
      ├─ 本地规则与学说判断
      ├─ 无协同保障的环境相关调度
      ├─ DAG 依赖验证与状态变化
      ├─ 汇总并同步处理冲突／交战
      └─ 写入事实、观察、任务结果与报告
      ↓
达到当日推进上限或稳定结束条件
      ↓
快照／结算摘要／供下一天使用的合法情报
```

不要公开固定的“侦察、移动、炮击、突击”微阶段；内部先以 3～4 轮事件传播作为实验参数。对同格竞争、对向穿越构造冲突集合，同时判定，不让 Java 集合遍历顺序制造免费守方身份。

### 7.3 可复现随机源

建议随机性按 `battleSeed + day + orderId + eventKind` 等稳定键派生，采用固定、跨平台一致的算法，并将规则版本、随机算法版本写入运行清单。地图生成、天气、行动时序采用分离的随机域；不直接用并发线程完成时间或遍历顺序决定结果。

机动速度差产生的追击能力是规则约束：较慢团不能靠调度随机性凭空追上已成功脱离、行动条件相当的更快侦察团。真实包抄、地形封堵、路线限制另行参与判定。

## 8. 战斗、机动与后勤实现

### 8.1 战斗模块

- 战斗以团交战、连级损伤表示；每种有效火力按照攻击目标、目标防护、地形、已展开状态、组织度和补给共同结算。
- 步兵连高基础 HP，装甲依靠防护、突击与反击，而不是统一高 HP；防御方在正面、准备充分的情形下略占优势。
- 真实目标分配与伤害类型必须可追溯，不能用“团里有两坦克连”给四个步兵连自动套坦克防护。
- 组织度是所有连共用的 HP 损伤函数；避免同时重复施加同一比例惩罚。
- 对纯远距攻击不强制开火方收到无缘无故的反击伤害。
- 数值公式封装为带版本的可测试规则，具体参数由 Doctrine Lab 校准。

### 8.2 正常移动与运输

正常移动由每个有效连队先计算指定路段／地形的速度和通行性，再取最小值，团作为一个整体占格。MVP 不模拟“快连暂时离团、慢连随后跟上”的隐形独立位置。

运输是独立状态：运输设施绑定道路或铁路线，承运物资或团，受载重、路段容量和队列约束；结束运输／遭攻击后的状态转换独立定义。运输活动本身记录可见的实体轨迹，并可被侦察与阻截。

## 9. 情报、通信与事件流

### 9.1 通信图

通信连与永久通信工事作为节点，按六角格距离与当前技术半径建边，初始半径暂取五格。固定工事主要有 HP，易被破坏；通信网络图与旅团建制关系图分别表示。

第 N 天的团级本地发现立即允许本团条件行为；正常上传到师部的情报在第 N+1 天供全局共享，相应连通单位届时可用，**无额外 N+2 延迟**。失联团的新观察保存在本地，直到合法上报；不会经渲染层泄露。

### 9.2 建议的日志契约

| 记录 | 用途 |
|---|---|
| `CommandAccepted` | 命令何时提交、校验并被哪个团／旅接收 |
| `WorldEvent` | 战场客观变化（移动、架桥、交战、战损） |
| `Observation` | 哪个单位在何时实际观察到什么 |
| `ReportDelivered` | 情报何时合法送达哪个指挥节点 |
| `DoctrineDecision` | 基于哪个知识快照、学说规则选了什么行动 |
| `OperationTransition` | DAG 节点为何 READY／RUNNING／DONE／FAILED 等 |

每条事件含 `gameId`、`day`、稳定序号、事件 ID、原因事件 ID、相关 `orderId`／`operationId`／`nodeId`、行为单位、位置和必要前后状态。开发者真实事件日志与面向师部的可见日志**不是同一条未经筛选的输出**；实验全知模式可读取前者。

命令和执行使用稳定 ID 去重，防止 HTTP 重试或多轮条件检查导致重复消耗弹药、重复移动和重复回合结算。可采用事件日志 + 周期性世界快照，满足回放与恢复需求；无需第一版就建设复杂事件溯源基础设施。

## 10. HTTP API 草案

以下路径为**建议资源模型**，正式实现时可统一前缀 `api/v1`，OpenAPI 从控制器路由、DTO、校验注解及必要的语义注解生成，并提供示例请求；不手工维护或提交生成的 OpenAPI 文件。服务端处理身份、命令归属、战区权限、游戏阶段与版本冲突。

| 动作 | 建议 API | 语义 |
|---|---|---|
| 创建场景 | `POST /api/v1/scenarios` | 创建可编辑草案 |
| 修改场景 | `PUT /api/v1/scenarios/{id}` | 修改初始状态，验证尺寸／编制 |
| 冻结场景 | `POST /api/v1/scenarios/{id}/revisions` | 形成不可变运行输入 |
| 创建对局 | `POST /api/v1/games` | 关联冻结场景、规则与种子 |
| 查询视图 | `GET /api/v1/games/{id}/view?mode=division` | 玩家可见状态 |
| 提交团命令 | `POST /api/v1/games/{id}/orders` | 军事任务，不是直接改 HP |
| 提交旅计划 | `POST /api/v1/games/{id}/operations` | 验证 DAG、旅属／战区 |
| 回合确认 | `POST /api/v1/games/{id}/turns/{day}/commit` | 标记一方已提交 |
| 回合推进 | 服务端在双方均确认后触发，或实验模式显式请求 | **每回合最多结算一次** |
| 事件查询 | `GET /api/v1/games/{id}/events` | 依视图／权限投影与过滤 |
| 实验批量运行 | `POST /api/v1/experiments` | 冻结输入和对照种子 |
| 实验结果 | `GET /api/v1/experiments/{id}` | 进度、汇总、日志引用 |

HTTP 请求写入应支持幂等键／稳定命令 ID；回合提交、结算和场景冻结要有明确的生命周期校验。长时间批量实验可先返回实验 ID，以轮询查询进度；MVP 不需要 WebSocket。

## 11. 本地 HTTP 安全与未来联机

### 11.1 单机本地进程

- 默认监听 `127.0.0.1`；端口由启动器发现，不依赖永远固定的 8080。
- 服务启动时使用强随机源生成本次运行有效的**不透明 Bearer Token**，通过仅当前用户可读的本地文件或受控启动通道提供；Web 经用户明确输入或受控启动方式取得，只在内存中持有，不提供无认证的“领取令牌”接口。
- 受保护 HTTP API 要求显式 `Authorization: Bearer ...`；服务端验证后才执行命令。玩家主动开启的 API 调试模式可将临时凭据交给 cURL／Bruno。令牌不可出现在 URL 和普通日志。
- 原生 Web 通过显式 Authorization 头使用 Bearer，不依赖 Cookie 自动认证；CSRF 配置须与实际认证机制对应，CORS 不能替代身份认证。优先同源部署，不开放跨域。
- 对 HTTP、场景与学说文件限制大小、数量、深度、图节点数、地图规模、回合重复调用与实验并发；文件导入导出防止路径穿越；不允许上传学说就执行任意代码。
- 单机上帝视角是**玩家主动选择的玩法**，不等于开放未认证的远程写接口。

### 11.2 未来联机边界

保留玩家／阵营／游戏实例／回合归属，双方锁定命令后统一结算。远程服务增加 HTTPS、独立玩家凭据、游戏房间授权、敌我情报投影和反滥用限制；本地所有者的全知玩法不能自动转化为远程对手的全知权限。

## 12. 原生 Web 客户端与地图表示

- M1.1 起按游戏工作台设计：作战地图占主要视野，右侧部署标签、底部实验/指挥记录同屏；连接/新建/档案放入弹窗。以 1980×1080 为最低目标显示器，主面板通过分页避免滚动，不把所有表单纵向堆叠成长网页。

- 使用原生 SVG／Canvas 绘制逻辑地形、道路与河流、单位／设施，以及战区边界、通信、后勤和专题图层；按静态／动态／交互层区分更新。
- 单个六角格团标**最多两个具象连队类型图标**：最大编制类型 + 不同且显著制约正常机动的类型；没有瓶颈仅显示一个。运输以独立状态标记呈现。
- 专题图层由 `PlayerView` 的**已知连队和有效能力**生成，例如反坦克连分布和反装甲能力；全知投影单独生成真实分布。前端不能偷偷遍历客观 WorldState 补全未知敌情。
- 图标采用清晰、游戏化的形象设计，不默认使用专业军标。首版 UI 以场景编辑、团详情、旅级 DAG、地图图层和日志回放为主。
- 使用异步 Fetch 和实验进度轮询，批量模拟在服务端执行，页面显示运行中状态并保持可操作；客户端不参与决定战斗胜负。不引入 React／Vue、图形或状态管理组件库。

## 13. 测试策略与 Demo 验收

| 类别 | 必须验证 |
|---|---|
| 规则单元测试 | 组织度来自战损、最慢连机动、HP 与防护分开、地形通行 |
| 调度测试 | DAG 依赖保序，独立调度允许自然保序／失序且可复现 |
| 追击测试 | 机动 6 已脱离部队在同等路线条件下不被机动 5 靠抽签追上 |
| 编制对照 | 2 装甲＋4 徒步步兵填线，与机动型编制有不同成本和战损表现 |
| 情报隔离 | 不可见敌情变化不改变尚未获知该情报的团级学说决策 |
| 报告时效 | N 当日本地行动，N+1 正常共享；失联不上报、无 N+2 额外等待 |
| 接敌正确性 | 同格争夺不因集合顺序赠予先手防守优势 |
| 幂等性 | 重复命令／结算 HTTP 请求不重复扣损、移动和推进日数 |
| 视图测试 | God view 与 division view 切换不改变团级行为；专题图层不泄密 |
| 端到端 | 仅用 HTTP 完成编辑、提交、结算、查询、回放和 A/B 实验 |

建议首批固定场景：架桥渡河、炮击后突击、装甲突破失败撤退、机械化侦察脱离装甲追击、装甲支援步兵填线、失联情报，以及单连阻击与驱逐。每次实验记录场景版本、规则版本、命令和随机种子；支持精确重放与结果差异对比。

## 14. 发行、源码交付与开发者体验

- 《战术编排》计划为商业 Source-Available：**购买者获得对应发行版本完整可构建源码**，但不默认允许重新公开分发完整游戏源码或商业复制游戏。
- 提供源码归档、全局 Maven 兼容版本说明、构建说明、POM 固定的依赖及插件版本和必要第三方许可证；可评估离线依赖归档，避免“有源码却多年后无法构建”。
- 不采用以阻止正版玩家研究为目的的强混淆或 DRM；本地服务安全保护的是玩家设备和数据。
- 美术、音乐、游戏商标及第三方素材按各自版权和实际授权交付；发布前核定 Source-Available 协议与游戏平台条件。
- 官方 HTTP API、学说和场景数据格式应有稳定版本及示例，便于玩家在不修改游戏代码的情况下使用 Bruno、cURL 与 AI 工具。

## 15. 分期路线

**M0：工程与安全入口**——纯 Java 模块、Spring Boot、全局 Maven、认证、输入边界与代码生成 OpenAPI。

**M1～M4：API 与 Web 同步迭代**——从 M1 场景编辑／冻结与原生 Web 地图开始，依次增加 WEGO、最慢连机动、战斗／学说、旅级 DAG 与通信情报，每个节点都有可操作 Web 切片和 HTTP 验收。

**M5～M6：完成 Doctrine Lab MVP**——地图／任务／日志联动和单次回放、配对多种子对照、七组场景回归、离线运行说明。完整雷达和完善专题图层延后。

**后续：正式战役与远期扩展**——战区和战役目标、长期科技与经济、更多地理类型、PvE 体验完善、联机与更多视图。

## 16. 尚需通过原型定稿的技术细节

战斗与组织度的精确公式、每回合内部迭代轮数与冲突终止条件、交通拥堵模型、具体通信消息送达实现、事件日志保留与快照频率、HTTP 路径和 DTO、选用的库版本、正式安装包组成及 Source-Available 许可证措辞，均需以实验和测试结果定稿。上述选择不得破坏已确定架构边界：**独立服务端、纯 Java 权威引擎、HTTP 为正式外部接口、原生 Web 只做客户端、可复现事件与局部认知隔离。**
